# The floor and ceiling of agent rules

A record of the register, made 2026-11-17. The index of the register sits in docs/decisions.md.

Made: the owner, 2026-11-17, issue 482. Context: two layers hold the permission rules of an agent session: the user layer that genixis writes, and the project layer that each repository tracks. The split worked in practice, but no text stated it as one rule, so an agent of a produced project guessed whether its own tools were allowed and where the grant lived. Issue 478 shows the cost of a guessed tool form. The issue proposed four pieces of text. The owner started the leg with the loop comment of 2026-11-17 and posted no change to the proposal. Decision: the user layer denies command forms, never a whole tool. A deny rule of the user layer names a flag, a command shape, or a file read. Each project allows the tools of its own stack through its tracked `.claude/settings.json`, and each allow rule of the project layer adds to the rules of the user layer. A deny rule of the user layer overrides every allow rule. A command that no allow rule covers stops at a prompt. A prompt means a missing rule, not a veto of the tool. One promotion path moves a tool up. The tool proves itself in the project layer of one project. Then the owner promotes it into the allow list of the user layer (modules/programs/cli/claude.nix). Alternatives that lost: a deny rule of the user layer that names a whole tool, because each produced project would lose the tools of its own stack. One allow list per project with no shared user layer, because each project would restate the read-only tools, and the copies would drift apart. A promotion by a machine, because evidence and decision stay apart (Layering and Trust item 3, docs/design.md). Consequences: the law lives in the User Settings Layer section of docs/agent-context.md. One sentence of the global CLAUDE.md (modules/programs/cli/claude/CLAUDE.md) carries the layering to every agent session, also to the sessions of produced projects. The runbook step for a produced project names the grant path (docs/runbook.md). Each new tool of a project stays a manual step of the owner: one settings rule and one AGENTS.md line. The settings machinery itself does not change. Status: accepted. Reopens: the user layer needs a deny rule that names a whole tool, or the harness changes how the two layers combine.
