# The remote-only WezTerm window layer

A record of the register, made 2026-11-18. The index of the register sits in docs/decisions.md.

Made: the owner, 2026-11-18, issue 520; the layer came from issues 101 and 141. Context: the WezTerm window layer put every tmux session of one user on one host on screen as one tab of one window titled user@host. The local half of it — the tab of `project open` from a local shell, the tab of a detached build, the tab of `wezterm-attach` — drew every local session into the GUI of the machine, while the workflows that need the grouping run over ssh: the delegated `project open user@host:dir` with its local attach tab, and the shells behind the socket forward of a remote host window. Two on-screen paths served one local shell, and the Necessity Tests of docs/design.md retire a path that no consumer needs. The owner retracted the local half on 2026-11-18 and kept the remote half. Decision: a local shell reaches its session through the terminal itself. Outside tmux, `project open` attaches the session in the current terminal; inside tmux, an ide window of another session comes in front of the client through select-window and switch-client; `wezterm-attach` attaches in place; and a detached build prints the attach hint on stderr. guiTabReachable answers true only behind the socket forward of a remote host window, so only that shell, the delegated open of remote.go, and `ide pop` reach the layer. Alternatives that lost: removing the remote half too, because the dev-server workflow depends on the tabs behind the forward; a config switch between the tab layer and the in-place attach, because it keeps a dead path alive; keeping the grouping and dropping the remote path, because the owner picked the opposite split. Consequences: the tool holds one on-screen path per shell class, the hint of a detached build names the attach command on every shell that no GUI reaches, and the lua events of the WezTerm config keep computing the titles of the host windows that the remote half reads. Status: accepted. Reopens: a local workflow needs the grouping of the host window, for example a person who wants every local session as one tab of one window.
