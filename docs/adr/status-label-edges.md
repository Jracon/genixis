# The status labels drive the loop beside the commands

A record of the register, made 2026-11-25. The index of the register sits in docs/decisions.md.

Made: the owner, 2026-11-22, issue 631 (the body of the issue carries the ruling, and the ruling quotes the session that filed it: "It is already prohibitive to interact with every entity manually." and "An important fact about this system is that it is not my career. It is a hobby."). Context: the human surface of the loop was the commands alone (docs/adr/commands-only-triggers.md), so every stage cost one human comment per entity, an issue with seeded readiness lines had no start at all, and the owner asked for starts that a person drives with standing visibility on the board. Decision: one family of mutually exclusive status labels drives the loop beside the commands: `status/needs-spec` is the rough status and starts a refinement leg on any issue content, `status/agent-ready` is ready and runs the readiness gate and the worker start of a `/loop` comment, `status/needs-review` is the report of an open pull request that a leg writes, and `status/verified` is the human-only confirmation. The labels sit in one scope, so the forge holds at most one per entity, and the exclusivity needs no change of the forge. The `needs-owner` label sits outside the scope, so a stopped thread keeps its status. The human-only names sit in `forge.humanLabels`, so the hook denies every agent write of them; a label change of the agent login starts no leg. The refinement leg refines the brief with the owner and reports, and no readiness check runs for its spawn; the gate keeps its place before every worker start. The commands keep their meaning until a later ruling retires them. Alternatives that lost: a `/refine` command on the loop, because the labels carry the same starts with standing visibility on the board and one surface for every stage; the commands-only surface unchanged, because the cost per stage stayed one human comment on every entity; the removal of the self-trigger rule without a bound, because the ruling restricts named actions to human approval and leaves leg breeding bounded; the `needs-owner` prose continuation as the needs-input channel, because the ruling asks for a remote channel that carries the requests alone. Consequences: the owner creates the labels on the forge, sets the key, and ticks the label events of the issue events on the webhook page, and until the ticks exist the poll fallback carries the edges alone; a label edge touches no wake state, so a stopped thread keeps its `needs-owner` mark beside its status; stage 2 relaxes the self-trigger rule for the transitions of a human-approved list, and stage 3 wires the needs-input status to the Matrix conversation of its entity. Status: accepted. Reopens: the human-approved action list of stage 2, and the Matrix room of stage 3.

Amended 2026-11-25, on the comment of the owner on pull request 669 (read: tea pulls 669 --comments), which asked for labels that better reflect an actual workflow and named it: "human-phrased issue with no formatting -> in-place issue refinement to standard template -> human input for clarification -> agent internal/external research -> implementation -> testing -> refinement -> review -> merge". Context: the four labels of the decision above held no member for the wait for a human answer: the refinement leg asked its questions in a comment and the readiness gate parked on a comment, so the board named neither wait, and the ready status stood on an issue whose brief was parked. Decision: the family holds five members; `status/needs-input` is the ask status, and it names the wait for a human answer. The refinement leg writes it when its report asks at least one question, and the readiness park sets it beside the park comment; a person sets it by hand under the same rule. It triggers nothing as a label change: the answer of the person is prose on the thread, and the amendment below rules the resume of that prose. The stages of the workflow map onto the family at its waits: the raw issue takes the rough status; the refinement to the template runs inside the refinement leg, in place when the agent login owns the issue and as a comment when it does not; the wait for clarification takes the ask status; the research runs inside the refinement leg and the worker leg, and no status names it; the release of the implementation takes the ready status; the testing runs in the gate of the worker leg and in the CI of the forge, and a red gate starts the nudge, so no status names it; the refinement of the change runs as the review cycle that the verdict of the reviewer wakes, and the report label stays on through the cycle; the review takes the report label; the merge follows the confirmation of `status/verified`. The re-set of a status is one add, because the exclusivity of the scope replaces the status that the issue holds; when the forge holds two status labels, the re-set is a removal and then the add, so the owner verifies the replacement on a test issue before the protocol runs (machine decision 35 of the dispatcher README). Alternatives that lost: a status label for every stage that a leg runs through, because a status names a wait where a person acts, and the motion of a leg between two waits is visible in the session, the branch, and the pull request; a rename of the four names of the reference set, because the issue pins the mapping of the reference set, and a rename would move the vocabulary that the deployment steps create before any loop ran on it. Consequences: the owner creates the fifth label on the forge beside the four; the hook key holds the same three human-only names, and the ask and report names stay outside it; stage 3 wires the ask status to the Matrix conversation of its entity, as the consequence above already ruled. Status: accepted. Reopens: nothing new; the reopens of the decision above stand.

Amended 2026-11-25, on the comment of the owner on pull request 669 of 15:53 (read: tea pulls 669 --comments) and on the answers of the owner in the windowed session of the worker leg of the branch, which asked for an automatic response from the ask status instead of a command set. Context: the amendment above left the resume of the ask status on the next status set or command comment of the person, so every answer cost one more human act. Decision: the prose answer is an edge. A plain comment of a person on an open issue that holds the ask status starts the refinement continuation on both trigger surfaces, the same shape as the needs-owner rule. The continuation folds the answers of the thread into the brief, then either asks its next question and writes the ask status again, or reports the brief final and clears the ask status, so the board names no wait that ended. The next stage stays with the person: the ready set runs the gate and the worker, and the agent-authored advance of a label waits for stage 2 of the issue. An issue that holds both the needs-owner mark and the ask status routes a plain comment through the needs-owner rule. Alternatives that lost: an answer command on the loop, because it costs one human comment per answer, the cost that the decision above names; the advance of the ready label by the continuation inside this stage, because the human-approved action list of stage 2 rules that transition. Consequences: the refinement prompt names the fold and the clear (machine decision 36 of the dispatcher README); the hook needs no change, because the ask name sits outside `forge.humanLabels` and its removal runs under the allow that the key gives. Status: accepted. Reopens: the human-approved action list of stage 2, and the Matrix room of stage 3, the reopens of the decision above.
